# Database model

The executable first-release definition is `migrations/001_initial.sql`. It creates the complete current schema directly from an empty database. All IDs are UUIDs generated by PostgreSQL or by the application before self-referential root insertion. Tenant ownership is duplicated on child tables so every access path has both an explicit predicate and an RLS boundary. JSONB holds validated configuration/output; relational columns hold lifecycle and concurrency fields. Costs are integer micro-US-dollars.

Key invariants:

- run status is a database enum and application transition policy is explicit;
- `version` increments on every run mutation;
- active lease fields are both null or both present;
- terminal and wait states cannot retain leases;
- a cancellation-requested run cannot be completed;
- step sequence and idempotency keys are unique per run;
- tool execution idempotency keys are unique per tenant;
- each approval freezes tool, arguments, canonical hash, idempotency identity, requester, approver role, risk, and separation policy;
- frozen approval fields and completed decisions are database-immutable;
- approval consumption is valid only after approval and is recorded once with its worker;
- audit and usage rows are append-only by repository convention.

The baseline installs `pgcrypto` and `vector`; lifecycle, step, approval, and model-attempt enums; the complete run/tool/approval/provider/context/memory/retrieval/connector/skill/orchestration/evaluation/observability schema; final indexes and constraints; and deterministic read-only demo products. Prompts and raw provider responses are not stored in model attempts.

Tool operation hashes, attempt ledgers, retry-safety metadata, reconciliation state and leases, and crash-recovery evidence are present from initial creation. Approval action identity, canonical hashes, requested roles, risk, separation policy, consumption evidence, and immutable proposal/decision triggers are likewise created in final form.

The baseline creates active/revoked user and service memberships, token revocations, the non-login least-privileged `durable_agent_api` role, its final grants, and one `tenant_isolation` policy with both `USING` and `WITH CHECK` on every tenant-owned table. Each authenticated API request opens a transaction, switches locally to that role, and sets transaction-local `app.tenant_id`; explicit tenant predicates remain defense in depth. Workers and migrations use the owner connection and remain responsible for cross-tenant scheduling. Applying the baseline requires a migration principal permitted to create and grant roles; a managed service may require a DBA to provision equivalent roles first.

Plans, summaries, checkpoint provenance, durable memory, pgvector documents/chunks, governed connectors and skills, supervisor child runs, frozen run configurations, evaluation evidence, and operational indexes are created directly in their current forms. Database triggers enforce run transitions, orchestrated completion, frozen approvals, and five evaluation immutability rules.

The initial public release supports bootstrap from an empty PostgreSQL/pgvector database. Future schema changes will be represented by reviewed forward migrations; this baseline does not promise compatibility with databases created from the superseded private development migration chain.

Migration execution uses `DATABASE_URL` and contains no Docker assumptions. PostgreSQL 16 is verified; 15+ is the current compatibility target. Compose supplies `pgvector/pgvector:pg16`; external or managed PostgreSQL must support `CREATE EXTENSION vector` or have an administrator provision it before migration.
