# Threat model

Assets are tenant prompts, traces, tool inputs/results, approvals, credentials, memory, documents, delegation graphs, child results, and costs. Clients, model output, documents, connector metadata, and tool/child results are untrusted. API identity, PostgreSQL, worker, provider, and tools are separate trust zones.

| Threat | Current control | Remaining limitation |
|---|---|---|
| Cross-tenant access | signed tenant claims, active membership, repository predicates, and a transaction-scoped restricted API role with PostgreSQL RLS | database-owner credentials and worker compromise remain cross-tenant authority |
| Duplicate execution | content-bound operation identity, attempt ledgers, lease ownership, safety-classified retries, fail-closed unknown effects with leased reconciliation, and a central guard preventing paused runs from requeueing while an effect remains unresolved | a tool without an external lookup remains manual; abort cannot revoke an already-issued effect |
| Approval bypass | signed identity/role claims intersected with membership roles, immutable validated proposals, tenant/role checks, separation of duties, idempotent decisions, leased exact resumption through `ToolExecutor` | JWT issuer or database compromise can subvert identity |
| Prompt injection | model has no direct DB authority; memory and retrieved chunks are labeled untrusted data, appended after canonical constraints, budgeted, and cannot write or execute without policy/authorization and canonical tool execution | semantic attacks in retained/retrieved text remain possible; labeling is not an isolation boundary |
| Memory poisoning | deliberate API writes preserve provenance; shared writes require management authority; model writes are quota-bound and approval-only; corrections and deletions remain inspectable | reviewers must judge truth and intent; lexical ranking is not a trust score and physical retention cleanup is manual |
| Unsafe SQL | allowlisted demo tool accepts one validated `SELECT` and executes under a restricted read-only role | semantic query cost and broader SQL safety remain limited to the seeded demo scope |
| Secret leakage | provider and connector secrets are environment-only; connector rows persist reference names, not values; attempts/audits omit credentials | process compromise can read environment; no vault integration or automated rotation |
| Network exfiltration | MCP uses operator-configured exact origins, URL/userinfo/redirect checks, DNS private-address screening, response/time bounds, role/agent/tool allowlists, approval, and durable rate limits; ingestion never fetches source URIs | underlying fetch performs its own DNS resolution, so DNS rebinding TOCTOU is not eliminated; model, embedding, and connector endpoints receive selected data |
| Denial of service | per-agent step, token, and cost budgets are enforced | tenant-wide quotas and rate limits are later work |
| Malicious documents | bounded caller-supplied text/Markdown/JSON only, no active-content rendering or URL fetch, tenant/owner predicates plus RLS, explicit untrusted-data framing, citations, and context budgets | no malware/content scanner, factual validation, or semantic prompt-injection guarantee; remote embedding services receive source text |
| Lease theft | owner and expiry checked transactionally | DB credential compromise remains critical |
| Provider compromise | providers cannot mutate lifecycle or execute tools directly | prompts/tool schemas leave the process; provider trust and retention terms apply |
| Malformed provider output | raw Zod schemas and canonical action validation fail closed | semantic prompt injection remains possible |
| Credential leakage | keys are environment-only and excluded from attempt metadata | process/environment compromise can expose keys |
| Framework bypass | only native engine enabled; all tools use canonical executor | future adapters require equivalent contract tests |
| Malicious MCP metadata | schemas are bounded/compiled without references; descriptions, server instructions, results, and annotations are labeled untrusted and cannot change risk/retry/approval policy | semantic prompt injection remains possible; a trusted operator must review allowed origins/tools |
| Cost exhaustion | persisted token/cost budgets checked before and after calls | provider-reported usage and configured rates can be inaccurate |
| Delegation abuse | explicit target/role allowlists, depth/fan-out/parallel limits, target and parent budget checks, ancestry-loop rejection, tenant foreign keys, and RLS | compromised supervisor authority can delegate misleading goals within its configured bounds; tenant-wide quotas remain later work |
| False supervisor success | durable waits, persisted child results in context, required-child checks in application and database, and no completion with active/failed/empty required children | optional-child failure policy is intentionally left to the supervisor and remains visible in trace |
| Child data leakage | child runs inherit the tenant but not arbitrary parent context; shared snapshots require explicit policy and are bounded | shared context can contain sensitive parent step output and must be enabled only for reviewed child agents/providers |
| Evaluation manipulation | suites are immutable versions, runs freeze agent configuration, scoring reads persisted terminal evidence, comparisons require one suite version, and RLS/roles isolate history | managers can design weak datasets or thresholds; deterministic rules do not establish semantic quality or factual truth |
| Telemetry leakage | structured logs redact sensitive key names and bearer values, avoid raw prompts/responses, and operational endpoints require `system_operator`; run metrics remain tenant-scoped | semantic secrets in innocently named fields cannot be detected reliably; deployment log access and retention remain operator responsibilities |
| Browser token theft | same-origin CSP, no inline scripts, framing denial, no tenant data in the public shell, and text-only rendering reduce exposure | session-storage bearer tokens remain readable by same-origin XSS; no secure-cookie BFF, refresh flow, or external IdP integration is implemented |

There is no secure code sandbox, password/login system, asymmetric or external identity-provider integration, automated HMAC rotation, provider-secret vault, malware scanner, or general untrusted-code execution. API RLS does not restrict the trusted owner-role worker path. Containerization alone would not create an adequate sandbox. These gaps block a production-readiness claim.
